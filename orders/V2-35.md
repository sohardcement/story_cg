# 工单 V2-35：入口测试不依赖网络；资源错误的捕获范围补全

工作目录、写入范围、git 规则同前，遵守 AGENTS 第 9、11 条。命令带 `PYTHONPATH=$PWD/src`。

## 背景（监工已查）

- V2-34 合入主线以后，监工在主线工作区跑全量测试。第一次有 1 个失败：`tests/test_v2_34.py::test_beats_guide_shows_wai_list_l2_not_a_cache_l3_through_the_entry`。断言信息里是子进程输出的 traceback。单独跑能过，第二次全量也是 797 passed。
- 原因判断：这个测试通过 `skill/story-cg/scripts/storycg beats-guide --character 芙莉莲` 走到身份解析，会访问真实的 Danbooru。`.v2` 里的 Danbooru 缓存比较全，主线工作区的缓存不全，所以测试结果受网络影响，时好时坏。
- 出现 traceback 说明还有一类网络异常没被 V2-33 加的资源错误处理接住，比如响应被截断时的 JSON 解析错误、超时、SSL 错误。

## 要做

1. **找出所有会访问真实网络的测试**，范围是全部测试。重点看那些用子进程调用 `scripts/storycg` 的测试。
   - 改成离线：用 `tests/fixtures/` 下的 Danbooru 缓存快照，或者注入假的传输层。
   - 加一个检查：测试运行期间一旦发出真实网络请求，就让测试失败。实现方式你定，比如在测试环境里把代理指向一个不可达的地址，或者用 `sitecustomize` 拦截。
2. **补全资源错误的捕获范围**：
   - `compile`、`beats-guide`、`make`、`resolve` 遇到网络或资源类异常时，一律输出 needs_user 的 JSON，以非零退出码结束，不出 traceback。这类异常包括超时、连接重置、SSL 错误、HTTP 4xx/5xx、响应体解析失败。
   - 只接网络和资源类异常。程序自身的 bug 不要吞掉，照常报错。
   - 每一类异常各加一个测试，都从真实入口用子进程跑。
3. 在主线工作区的环境下证明测试不依赖缓存：参考 V2-26 的做法，把 `cache/danbooru` 指向一个空目录，再跑全量测试，结果全部通过，并且没有发出任何网络请求。
