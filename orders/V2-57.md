# 工单 V2-57：视觉审核每次请求加硬的总时长上限（D95）

用户决定（D95，2026-10-14）：修 D94 发现的缺陷——一次视觉审核请求可以无限挂住。

工作目录 `/work/workspace/manga_skill/.v2`（分支 `v2`）。开工时 HEAD 是 V2-56 验收后的提交，监工会在派工时告诉你基线测试数。写入范围、git 规则同前，遵守 AGENTS 第 9、10、11 条。所有 python 和 pytest 命令都带 `PYTHONPATH=$PWD/src`，pytest 的 `--basetemp` 放在 `.pytest-tmp/` 下。

## 背景（监工已核实）

- D94 配对比较里，任务 `jobs/cg-aedcca1147e0`（主线，只读）07:59:51 发出一次审核请求（`review_log.jsonl` 里 purpose `cand_01_03_identity_outfit`）后 35 分钟没有进展：连接一直 ESTAB，进程在 poll 里等；同一时刻视觉服务对一个小请求 1.3 秒就答了。监工结束了进程，`storycg resume` 续跑完成。
- 原因：`review.VisionClient.call`（`review.py` 约 155–161 行）给 `self.http.post` 传的 `timeout=180`，在 httpx 里是连接、读、写各自的超时；读超时只看\"多久没收到数据\"，不限一次请求的总时长。服务端隔一阵回几个字节、或连接半死时，它永远不触发。`max_seconds` 那层预算只在两次调用之间检查，流水线里还是 `None`（V2-54）。
- 模型服务的请求只有这一处（全仓库 `chat/completions` 只出现在 `review.py`）。定妆图审核、候选审核、并排挑选、终审都经过 `VisionClient.call`。
- 历史数据（主线 `jobs/*/review_log.jsonl`，2535 次调用）：成功返回的最长 117.9 秒，中位数 17 秒；超过 120 秒的成功调用一次都没有。耗时正好 180 秒左右的都是读超时报错。
- 测试里给 `VisionClient` 注入的是带 `httpx.MockTransport` 的真 `httpx.Client`（`tests/test_review.py` 等）。读超时已有测试：`test_client_failure_is_logged_and_failed`，结果是 `status` 为 `fail`、结论\"未通过\"、日志里有 response 记录。

## 要做

1. `VisionClient.call`：从发出请求到拿到完整响应，**墙钟时间超过 180 秒就放弃**，误差不超过 5 秒。两种情况都要拦住：
   - 服务端一直不回数据；
   - 服务端隔一阵回几个字节（每块之间不到 180 秒，但总时长没有尽头）。
   - 设了 `max_seconds` 时，上限取 180 和剩余预算里小的那个（现在的逻辑保留）。
2. 超时按现有的失败路径处理：`result['error']` 写 `TimeoutError: vision request exceeded <N> s`（N 是实际用的上限），`status` 不是 pass，照常写 response 日志，`call` 正常返回，任务接着跑。和现在的读超时一样，不抛到调用方。
3. 180 秒作为默认值，给 `VisionClient.__init__` 加一个参数（比如 `request_max_seconds=180`），只为测试能用小值；流水线里的调用方都不传，用默认值。
4. 实现方式自定，报告里说明为什么它能满足第 1 条的两种情况。提示：httpx 没有总时长超时；一种做法是把现有的 `self.http.post(...)` 放进守护线程，主线程最多等到截止时间，过时就按超时处理（被丢下的线程不能再写日志或改 `self` 的计数）；另一种是流式读取、每块检查截止时间，但要说明\"一块数据刚到、之后完全不回\"时总时长会不会超过上限。
