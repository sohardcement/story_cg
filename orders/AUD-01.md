# 工单 AUD-01：v1 代码审计（不出图，不改代码）

先读 `TASK-CAP.md`（重点是 §3）、AGENTS.md（含补充禁令第 6、7 条），以及 PROGRESS.md 的工单列表和决策记录（D1–D29）。

## 目标

弄清 `src/storycg/` 里每个模块：在实际任务中是否被调用，有没有验证证据，是否只为道具服务。产出 `audit/AUDIT.md`，每个模块一行。**只给建议，不删、不改任何代码。**

## 方法

1. **静态分析**：从入口（`storycg/__main__.py` 的 make / approve / status / resume / deliver，以及 worker 进程）出发，画出调用关系，列出从入口可达和不可达的函数与模块。只被测试或 `tools/` 脚本引用的，单独标注。
2. **运行证据**：扫描 `jobs/*/` 和 `runs/*/` 里的日志、manifest、cycle.json、review.json、plan_log.json、agent_llm_log.json 等，统计每个功能在真实任务里留下痕迹的次数和任务目录，比如修复方法各用了几次、L1–L4 各出现几次、定妆缓存命中几次、区域重绘是否出现过。区分开发期一次性运行（P 工单的 runs/）和 Hermes/CLI 正式任务（jobs/）。
3. **验证证据**：从 PROGRESS.md 的工单列表与校准结果中，为每个模块找出验证它的工单号和证据路径（图片、拼图、校准文件）。没有就写"无"。
4. **道具相关**：标出只为道具服务的代码，比如道具登记、逐件清点、归属与状态、possession_swap、物体脱离规则。和人物共用的部分，写清哪些分支只服务道具。
5. **如果静态分析和日志都无法判断**某个模块是否在用，可以在报告里提议跑一次完整任务做覆盖追踪，但本工单不要自己跑。

## AUDIT.md 的格式

每个模块一行，列为：文件、行数、作用（一句话）、实际任务中是否调用（是 / 否 / 只在开发期 / 只在测试，附次数）、验证证据（工单号和路径）、是否只为道具、建议（保留 / 简化 / 删除）和理由。

表格之后写：

- 汇总：总行数，以及建议删除、简化的行数各占多少；
- 只被测试引用的死代码清单；
- 你不确定的判断，以及原因。

## 不许做

出图；调用视觉模型；修改 `src/`、`skill/`、`config/`、`tests/`、`tools/` 或任务目录；git commit。新文件只放在 `audit/`。

出图 0；时长 60 分钟。

`audit/AUDIT.md`、`audit/` 下的辅助数据（调用图、日志统计脚本及其输出），以及 `reports/AUD-01.md`。报告写清验证方法，给出可以直接重跑的统计命令。
